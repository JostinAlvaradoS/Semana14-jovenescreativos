Antes de todo, el escenario.

Internet son dos computadores hablando

Cliente

El que pide

Tu navegador. Manda un mensaje: "dame la página tal". Es lo que ustedes han sido todo el programa.

⇄
Servidor

El que responde

Un programa encendido 24/7, escuchando. Recibe la petición y contesta: "toma, aquí está".

Cliente y servidor son roles, no aparatos — como comprador y vendedor. Guarden esta idea: al final de la sesión ustedes cambian de bando.

Idea 1 · El problema.

JavaScript hace una sola cosa a la vez

Es una sola persona con una lista de tareas: un solo hilo.

  • Pedir datos a otro computador puede tardar 2 segundos.
  • Si esa única persona esperara parada… la página entera se congela: sin clics, sin animaciones, sin escribir.
  • Y eso es inaceptable en cualquier app real.
Pregunta al chat: ¿qué operación de TU proyecto de emprendimiento probablemente "tarda"?

Idea 2 · La solución: asincronía.

El mesero no espera frente a la cocina

Mesero

El hilo de JS

Toma el pedido, lo entrega a la cocina… y sigue atendiendo otras mesas.

Cocina

El servidor / disco

Hace el trabajo lento por fuera, sin bloquear al mesero.

Aviso

La promesa resuelta

"¡Plato listo!" — el mesero reacciona y lo entrega cuando puede.

Asincronía = encargar lo lento, seguir trabajando, y reaccionar al aviso.

  • Lo encargado va a una cola.
  • La cola solo se atiende cuando todo lo síncrono terminó.
  • El 0 no significa "ahora": significa "apenas puedas".

Idea 3 · Promesas.

El comprobante de un valor futuro

Como el número que te dan en un local de comidas: aún no hay comida, pero hay garantía de un final.

pending

Esperando

La operación no ha terminado. Tienes el número en la mano.

fulfilled

Cumplida

Llegó el valor → se ejecuta el .then.

rejected

Rechazada

Hubo un error → se ejecuta el .catch. Y .finally corre siempre.

Regla de oro: una promesa cambia de estado una sola vez. Nunca queda en el limbo.

Idea 4 · async / await.

Lo mismo, escrito legible

obtenerUsuario()
  .then(u => usar(u))
  .catch(e => avisar(e))
  .finally(() => cerrar());
=
async function cargar() {
  try {
    const u = await obtenerUsuario();
    usar(u);
  } catch (e) { avisar(e); }
  finally { cerrar(); }
}
  • await solo vive dentro de funciones async.
  • La "pausa" es solo dentro de esa función — nada se congela.
  • Por debajo son las mismas promesas: es azúcar sintáctica.

Idea 5 · fetch — el corazón de hoy.

El sobre y la carta

  • Primer await: llega el sobre — la respuesta HTTP. Código 200, todo bien. Pero la carta sigue adentro.
  • Segundo await: respuesta.json() abre el sobre y convierte la carta en objeto de JS.
  • Olvidar el segundo = leerle el nombre a un sobre cerrado → undefined.
Aquí ustedes son el cliente: piden, PokéAPI responde.
const respuesta = await fetch(url);
// 📬 el sobre

const datos = await respuesta.json();
// ✉️ la carta, ya como objeto

datos.name  // "pikachu"

Paréntesis de seguridad.

Todo lo del navegador es público

Frontend = vitrina

F12 lo revela todo

Tu JS completo, las URLs que consumes, cada petición y su respuesta (pestañas Sources y Network). Lo que llega al navegador del usuario, le pertenece al usuario.

Backend = trastienda

El servidor guarda secretos

El código de server.js nunca viaja al navegador: el cliente recibe la respuesta, jamás la receta. Ahí viven las claves y la lógica sensible.

Nunca pongas una API key en el frontend. ¿Dónde va entonces? En un servidor propio… que es exactamente lo que sigue.

Idea 6 · Node.js — el cambio de bando.

Ser el que responde

  • Node ejecuta JavaScript fuera del navegador (mismo motor de Chrome: V8).
  • Sin página → no hay document. A cambio: archivos, red y el módulo http.
  • Un servidor solo hace dos cosas: escuchar en un puerto y responder.
  • El programa no termina: queda vivo, esperando peticiones.
const http = require("http");

http.createServer((req, res) => {
  res.end("Yo soy el que responde");
}).listen(3000);
En el fetch fuiste el cliente. Con Node eres el servidor. Mismo lenguaje, otro lado del mostrador.
